# EvalHub Guidellm Provider Fix & Benchmark End-to-End Verification

## Primary Objective
Fix the guidellm benchmark failure in the promotion pipeline. The benchmark task submitted to EvalHub but got 404/401 because the `guidellm` provider was not registered in the EvalHub CR.

## Root Causes (3 distinct issues fixed)

### 1. EvalHub guidellm Provider Not Registered (CRITICAL)
**Symptom:** `POST /api/v1/evaluations/jobs` → `404 "The provider resource 'guidellm' was not found"`
**Cause:** The EvalHub CR `spec.providers` only listed `[garak, garak-kfp, lm-evaluation-harness]`. The TrustyAI operator created the provider ConfigMap (`trustyai-service-operator-evalhub-provider-guidellm`) but the EvalHub CR didn't activate it.
**Fix:** Added `guidellm` to the EvalHub CR providers list via `oc patch`, then committed to GitOps (`gitops/components/evalhub/evalhub-cr.yaml`):
```yaml
spec:
  providers:
  - garak
  - garak-kfp
  - lm-evaluation-harness
  - guidellm
```
Commit: `d8ad15e`

### 2. Staging Namespace Missing EvalHub Tenant Label
**Symptom:** EvalHub authorization maps `X-Tenant` header to namespace. Without the tenant label, EvalHub may reject requests.
**Fix:** Labeled staging namespace: `oc label ns staging evalhub.trustyai.opendatahub.io/tenant=`
GitOps already has `staging-namespace.yaml` with this label — it just wasn't applied to the cluster namespace.

### 3. Guidellm Benchmark Rate Validation (ALREADY FIXED from July 28)
**Symptom (if rate=1):** Guidellm sweep profile validation error: `sweep_size >= 2 required, got 1`
**Confirmed working:** The controller already defaults to `guidellm-rate: 4.0`. Tested manually with rate=1 (fails) and rate=4.0 (succeeds). The `community-guidellm:v0.2.0` adapter always maps benchmark requests to `--profile sweep`. With rate=4.0, the sweep has multiple rate levels → works. With rate=1, single level → fails. This was fixed July 28 and confirmed still valid.

## Key Learnings
1. EvalHub `spec.providers` controls which benchmarks are available. Provider ConfigMaps from the TrustyAI operator are NOT sufficient — they must be listed in the EvalHub CR.
2. The `community-guidellm:v0.2.0` adapter always generates `--profile sweep` internally. The benchmark `id` (constant, concurrent, etc.) influences parameters but not the profile selection.
3. Guidellm sweep needs `sweep_size >= 2`. Rate=4 gives enough rate levels. Rate=1 fails. NEVER set rate below 2.
4. EvalHub Kubernetes Jobs are created in the tenant namespace (staging), not the EvalHub namespace.
5. The benchmark task (`quay.io/jhurlocker/guidellm-benchmark:v0.1.5`) submits via `/api/v1/evaluations/jobs`, polls for completion, and saves results to workspace.
