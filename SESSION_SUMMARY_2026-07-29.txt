# Session Summary — 2026-07-29
# Operator Auto-Token Generation, MaaS Deployment RBAC, and EvalHub 401 Fix

## Primary Objective
Fix the EvalHub 401 error in the security-scan step, ensure the MaaS deployment works end-to-end in the promotion pipeline, and eliminate all manual credential management. The operator must auto-generate tokens and set up all required RBAC automatically.

## Key Accomplishments

### 1. EvalHub Token Auto-Generation (CRITICAL)
Replaced the static `evalhubToken` secret approach with dynamic SA token generation via the Kubernetes `TokenRequest` API.

#### The Problem
- The `evalhub-credentials` secret stored a manually created OAuth token.
- The runtime-config GitOps component removed the `token` field from the secret (only `url` remained).
- Operator code read `secret.Data["token"]` which was empty → `s.evalhubToken` stayed empty → pipeline received empty `evalhub-token` → security-scan got 401.

#### The Solution
File: `operator/internal/controller/modelrequest_controller.go`
```go
func (r *ModelRequestReconciler) generateServiceAccountToken(ctx context.Context, namespace, saName string) (string, error) {
    tr := &authenticationv1.TokenRequest{
        Spec: authenticationv1.TokenRequestSpec{
            ExpirationSeconds: ptrInt64(86400),  // 24 hours (was 900 = 15 min)
        },
    }
    sa := &corev1.ServiceAccount{ObjectMeta: metav1.ObjectMeta{Name: saName, Namespace: namespace}}
    if err := r.SubResource("token").Create(ctx, sa, tr); err != nil {
        return "", fmt.Errorf("failed to create token for %s/%s: %w", namespace, saName, err)
    }
    return tr.Status.Token, nil
}
```
Called from `resolveSecrets()` when `s.evalhubToken == ""` (i.e., no token in the secret).

#### Token Lifetime
- **DO NOT set ExpirationSeconds below 86400 (24 hours)**. The sandbox pipeline runs compliance → GPU advisor → GPU sharing → deploy → security-scan, which can take 10+ minutes. The promotion pipeline takes even longer. A short-lived token will expire mid-pipeline.
- The token is generated once per PipelineRun creation and passed as a param. It must outlast the entire pipeline run.

#### RBAC Required
Operator SA must have `serviceaccounts/token` create verb (in ClusterRole):
```yaml
- apiGroups: [""]
  resources: ["serviceaccounts/token"]
  verbs: ["create"]
```

#### Deployment Gotcha
- When building the operator image, `podman` aggressively caches layers. A `COPY internal/` may hit cache even if source files changed. **Always use `--no-cache` or a unique timestamp tag** when the Go source changes.
- Even with `imagePullPolicy: Always`, CRI-O on OpenShift nodes may cache images by tag. **Always use a unique version tag** (e.g., `v0.2.N-$(date +%s)`) after code changes to guarantee a fresh pull.
- ArgoCD self-heal will revert any `oc set image` changes. **Update the GitOps `deployment.yaml` and let ArgoCD sync**, or disable auto-sync temporarily.

### 3. Operator `edit` ClusterRoleBinding
The operator creates `pipeline-edit` RoleBindings in promotion namespaces which delegate the `edit` ClusterRole. For this to work, the operator's own SA must hold the `edit` ClusterRole.

File: `gitops/components/operator/clusterrolebinding-edit.yaml`
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: modelops-operator-edit
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: edit
subjects:
  - kind: ServiceAccount
    name: modelops-operator
    namespace: modelops
```
Without this, promotion pipelines fail with `RBACSetupFailed` because the operator cannot create RoleBindings delegating `edit`.

### 6. MaaS CRD RBAC (CRITICAL — avoid repeating this work)

#### The Problem
The pipeline SA (`sandbox:pipeline`) needs to create MaaS CRDs in the promotion namespace:
- `serving.kserve.io/v1alpha2`: `llminferenceservices`, `llminferenceserviceconfigs`
- `maas.opendatahub.io/v1alpha1`: `maasauthpolicies`, `maasmodelrefs`, `maassubscriptions`, `externalmodels`, `tenants`

The `edit` ClusterRole only covers standard Kubernetes resources, not CRDs.

#### The Solution

**1. ClusterRole `pipeline-maas-deployer`**
File: `gitops/components/operator/clusterrole-maas.yaml`
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: pipeline-maas-deployer
rules:
  - apiGroups: ["serving.kserve.io"]
    resources: ["llminferenceservices", "llminferenceserviceconfigs"]
    verbs: ["*"]
  - apiGroups: ["maas.opendatahub.io"]
    resources: ["maasauthpolicies", "maasmodelrefs", "maassubscriptions", "externalmodels", "tenants"]
    verbs: ["*"]
```

**2. Operator ClusterRole (must include MaaS CRDs for delegation)**
File: `gitops/components/operator/clusterrole.yaml`
The operator's own ClusterRole (`modelops-operator-controller`) must include the same CRD permissions. Kubernetes RBAC escalation prevention: an SA cannot delegate permissions it doesn't itself hold.
```yaml
  - apiGroups: ["serving.kserve.io"]
    resources: ["llminferenceservices", "llminferenceserviceconfigs"]
    verbs: ["*"]
  - apiGroups: ["maas.opendatahub.io"]
    resources: ["maasauthpolicies", "maasmodelrefs", "maassubscriptions", "externalmodels", "tenants"]
    verbs: ["*"]
```

**3. Operator creates RoleBinding in promotion namespace**
File: `operator/internal/controller/modelrequest_controller.go` → `ensurePromotionNamespaceRBAC()`
```go
maasRb := &rbacv1.RoleBinding{
    ObjectMeta: metav1.ObjectMeta{Name: "pipeline-maas-deployer", Namespace: targetNS},
    RoleRef: rbacv1.RoleRef{APIGroup: "rbac.authorization.k8s.io", Kind: "ClusterRole", Name: "pipeline-maas-deployer"},
    Subjects: []rbacv1.Subject{{Kind: "ServiceAccount", Name: "pipeline", Namespace: sourceNS}},
}
```

**4. RoleBinding subject namespace is SOURCE (sandbox), NOT target (staging)**
The PipelineRun runs in the `sandbox` namespace. Its pods use the `sandbox:pipeline` SA, not `staging:pipeline`. The `ensurePromotionNamespaceRBAC` function signature was changed:
```go
// OLD: func (r *ModelRequestReconciler) ensurePromotionNamespaceRBAC(ctx context.Context, namespace string) error
// NEW: func (r *ModelRequestReconciler) ensurePromotionNamespaceRBAC(ctx context.Context, targetNS, sourceNS string) error
```
All RoleBinding subjects reference `sourceNS:pipeline` (sandbox). This applies to `pipeline-edit`, `pipeline-maas-deployer`, and `pipeline-evalhub-submitter` ClusterRoleBindings.

## PlatformConfig ArgoCD Auto-Sync Warning
When removing fields from PlatformConfig via `kubectl apply`, Kubernetes **does not** delete fields that are not in the new spec. Use a JSON patch:
```bash
kubectl patch platformconfig -n sandbox default-modelops-platform --type json \
  -p '[{"op":"remove","path":"/spec/maasServingNs"},{"op":"remove","path":"/spec/maasPolicyNs"}]'
```
If ArgoCD auto-sync is enabled for `modelops-runtime-config`, it will revert any direct cluster edits. Either disable auto-sync temporarily or commit the fix to Git.

### EvalHub Token
- **NEVER** set `ExpirationSeconds` below 86400 (24 hours). Pipelines exceed 15 minutes.
- **NEVER** revert to static `evalhubToken` from secrets — use `generateServiceAccountToken`.
- The `serviceaccounts/token` create verb must remain in the operator ClusterRole.
- The `evalhub.trustyai.opendatahub.io/tenant` label must be on the sandbox namespace.

### MaaS Deployment
- **NEVER** add `maasServingNs` or `maasPolicyNs` back to PlatformConfig — they override the targetNamespace default.
- **NEVER** revert RoleBinding subjects to `staging:pipeline` — PipelineRun pods run as `sandbox:pipeline`.
- **NEVER** remove `pipeline-maas-deployer` ClusterRole or the MaaS CRD permissions from the operator ClusterRole.
- **NEVER** add namespace get/create/label back to `maas_deploy.py` Step 1 — pipeline SA lacks cluster-scope permissions.

### Build & Deploy
- **ALWAYS** use `--no-cache` or a unique timestamp tag when Go source changes.
- **ALWAYS** update `gitops/components/operator/deployment.yaml` with the new image tag.
- If CRI-O caches an old image digest, bump to a completely new unique tag.
