### 2. EvalHub SA Token Authentication (CRITICAL — avoid repeating this work)
EvalHub requires an authenticated OpenShift principal for every API request (except `/health`). The pipeline's service account can be used, but needs specific RBAC.

#### The Problem
- `evalhub-credentials` secret stored a user OAuth token that expired every 24 hours.
- Pipeline SA token was rejected by EvalHub with `unable_to_authorize_request`.
- EvalHub performs Kubernetes `SubjectAccessReview` checks against `trustyai.opendatahub.io/evaluations` and `mlflow.kubeflow.org/experiments`.

#### The Solution
1. **ClusterRole** (must exist in cluster):
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: pipeline-evalhub-submitter
rules:
  - apiGroups: ["trustyai.opendatahub.io"]
    resources: ["evaluations"]
    verbs: ["create", "get", "list", "delete"]
  - apiGroups: ["mlflow.kubeflow.org"]
    resources: ["experiments"]
    verbs: ["create", "get", "list", "delete"]
```

2. **ClusterRoleBinding** (binds pipeline SA to above role):
```bash
kubectl create clusterrolebinding pipeline-evalhub-submitter \
  --clusterrole=pipeline-evalhub-submitter \
  --serviceaccount=sandbox:pipeline
```

3. **Controller:** Passes `evalhub-token: "auto"` instead of `secrets.evalhubToken`.
   File: `operator/internal/controller/modelrequest_controller.go`
   Both `buildSandboxPipelineParams` and `buildPromotionPipelineParams`.

4. **Task wrappers:** Both `security-scan` and `guidellm-benchmark` tasks read SA token
   from `/var/run/secrets/kubernetes.io/serviceaccount/token` when `EVALHUB_TOKEN` is empty or `"auto"`.
   - `security-scan`: Uses `command: [/bin/sh, -c]` + `args: [...]` with `python /usr/local/bin/security-scanner full`
     (the security-scanner binary has execute-permission issues when run via `script:` — must use `python` prefix)
   - `guidellm-benchmark`: Uses `script:` with Python-based EvalHub API integration

5. **EvalHub tenant label:** Target namespaces MUST have:
   ```
   evalhub.trustyai.opendatahub.io/tenant=true
   ```
   The `deploy-model` task applies this label automatically:
   ```
   oc label ns "$(params.namespace)" evalhub.trustyai.opendatahub.io/tenant=true --overwrite
   ```

### 3. Guidellm Benchmark Parameters (CRITICAL)
EvalHub's GuideLLM provider requires specific benchmark parameters. If omitted, EvalHub uses provider defaults which may run indefinitely.

#### Required Parameters
- `rate`: Must be >= 2 (rate=1 causes `sweep_size=1` → invalid → guide fails)
- `max_seconds`: Recommended 15
- `max_requests`: Recommended 2
- `id`: `constant` (supported by EvalHub provider; `sweep` may use unpredictable defaults)

#### Controller Defaults
File: `operator/internal/controller/modelrequest_controller.go`
```
addParam(&p, "guidellm-profile", "constant")
addParam(&p, "guidellm-rate", "4.0")          // MUST be >= 2
addParam(&p, "guidellm-max-seconds", "15")
addParam(&p, "guidellm-max-requests", "2")
```

#### Model URL
Use INTERNAL service URL, not external route:
```
http://<release-name>-predictor.<namespace>.svc.cluster.local:8080/v1
```
The controller builds this as `$(params.release-name)-predictor.$(params.target-namespace).svc.cluster.local:8080/v1`.

## DO NOT CHANGE / REGRESSION RISKS

### EvalHub Auth
- NEVER revert to `secrets.evalhubToken` — it expires. Always use `"auto"`.
- NEVER remove the `pipeline-evalhub-submitter` ClusterRole/ClusterRoleBinding.
- NEVER remove the EvalHub tenant label from deploy-model task.

### Guidellm Benchmark
- NEVER set `guidellm-rate` to 1 or below — causes EvalHub `sweep_size=1` error.
- NEVER use external route URL for target — use internal `svc.cluster.local`.
- NEVER omit `max_seconds`/`max_requests` — EvalHub may run indefinitely.

### Task Execution
- `security-scan` binary has execute-permission issue when run via `script:` or `exec`.
  Must use `command:` + `args:` approach with `python /usr/local/bin/security-scanner full`.
- `guidellm-benchmark` Python binary also has permission issues.
  Must use `script:` approach with inline Python calling EvalHub API directly.

## Known Infrastructure Issues
- **Trivy DB:** The compliance-artifact-scan Trivy step may fail with "image scan error: unable to read the file: unexpected EOF". This is a Trivy database/infrastructure issue, not a code issue. When Trivy fails, the pipeline halts (gate fails). Workaround: retry or fix Trivy DB connectivity.
- **EvalHub benchmark timing:** GuideLLM benchmark duration is controlled by EvalHub's internal provider configuration, not solely by API parameters. Parameters we pass influence but don't fully control run time.
